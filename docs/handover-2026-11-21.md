# Handover, 2026-11-21

Written at the end of a long session (about 93 rounds) so the next person or
agent starts from facts rather than from the changelog. Everything here was
measured; where it was not, it says so.

## What is running

- **Polls**: quick every 15–30 min per platform, full every 6 h. HackerOne,
  Bugcrowd, Intigriti, YesWeHack. 1,346 programs, about 50,000 in-scope targets.
- **Scan handoff**: on, every 30 minutes, eight oldest candidates per batch,
  one task per program, named `huntdeck-<platform>-<program>-<stamp>`. Targets are
  recorded before the scanner is asked to start, so a refused start does not
  produce a second task for the same target.
- **Scan cluster** (ScopeSentry, three nodes): was saturated all night. Nine tasks
  running, ten queued, seven failed. The failures are the scanner's own reaper:
  "no progress for 15 minutes, not in any node's queue" - i.e. a node restarted or
  paused under memory pressure and the task stopped reporting.

## Known gaps, all documented in docs/changes-2026-11.md

1. **A task created but not started is never retried.** The handoff key has no
   way to list tasks or read a task's status (`get_task_progress` returns module
   timings only - checked with a real id). Fix options and the reason it was not
   done are in the changelog.
2. **The handoff keeps creating tasks it cannot start.** Every thirty minutes it
   creates up to four; the scanner refuses to start them while a node holds three.
   A backoff is described, not written.
3. **The login browser stays open** after a successful sign-in even with
   `HUNTDECK_VNC` off: one Chrome and one Xvfb, 273 MB measured. Closing it needs a
   login to verify against.

## What broke tonight, and what now catches it

| Outage | Cause | Guard that exists now |
|---|---|---|
| 20 minutes | The WAL checkpoint ran with `context.WithoutCancel` and no deadline, held the database, and every later read queued behind it | The checkpoint is bounded at 5 s; the read-only CLI commands give up after 90 s and say why |
| 6 minutes | A startup sweep ran three lines before the store existed, dereferenced nil, and the container crash-looped | `TestOpenAppWiresEveryPart` builds the app in a temp directory; putting the bug back makes it panic |

The deploy script failed four ways in one night (a nested quote the remote shell
mis-parsed, a lock that refused when nothing was running, a lock check that
`pipefail` turned into a silent exit, and the concurrency the lock was written
for). It has a lock and a dead-build detector; `bash -n` is not a test.

## What needs a human

1. **Capacity.** Three node containers sit at 90–100% of their memory limit with
   concurrency 2. Lowering `maxGoroutineCount` to 1 halves the peak at half the
   throughput; raising the container limit is the other answer. Every failed scan
   tonight traces back to this.
2. **HackerOne website login.** `/users/sign_in` answers 403 to curl through the
   relay, mihomo and direct alike (Cloudflare's browser check), and Chrome reports
   `ERR_CONNECTION_CLOSED` on navigate. It retries on a 30 min → 1 h → 2 h → 4 h
   backoff. Diagnosing it needs a real login attempt with the browser visible.
3. **Twenty vulnerabilities are waiting for triage** in the scanner, six of them
   found by tonight's scans.

## How to check it quickly

```sh
docker exec huntdeck-huntdeck-1 ./huntdeck version      # what is deployed
docker exec huntdeck-huntdeck-1 ./huntdeck doctor       # 25 lines, one per dependency
docker exec huntdeck-huntdeck-1 ./huntdeck doctor --short   # failures and warnings only
scripts/bench.sh --check                                # page and API budgets
go test ./... && make lint                              # 37 packages, 0 issues
```

The doctor covers the data directory, the schema, the key, disk, the proxy's
actual egress, each website login, running polls, notifications, freshness, the
queue's history, the scanner's nodes and headroom, the Bugcrowd submission
allowance, and now whether the scan handoff has stalled.
