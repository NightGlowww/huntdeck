# HuntDeck web UI — loading, refresh, scroll

Audit of the server-rendered UI in `internal/web` (templates, plain CSS, vanilla JS). No project files
were changed; this is the only file written. Ranked by how often a normal user hits each one, with
file:line evidence and a fix that fits the no-build design.

Read: `templates/*.html`, `templates/partials/*`, `static/css/*.css` (joined in name order), `static/*.js`,
and the list handlers — `programs.go`, `targets.go`, `changes.go`, `disclosed.go`, `statspage.go`, `board.go` —
plus `render.go`, `pager.go`, `conditional.go`, `settings.go`, `acceptinvite.go`, `cmd/huntdeck/poller.go`.

## What exists today (so the gaps are precise)

- **Busy state:** one spinner, `.button.is-busy, button.is-busy::after` (`static/css/25-accounts.css:43-50`),
  driven by two independent `submit` handlers: `static/app.js:82-90` (class + `aria-busy` + disable) and
  `static/app.js:539-557` (rewrites the button's text to "Saving…", restores at **8 s**). Both are bound to
  `submit` — POST forms only. Nothing watches GET navigation.
- **Live refresh:** exactly one mechanism, `[data-live-refresh="seconds"]` (`static/app.js:466-483`), used in
  exactly one place: Settings' poll history while a poll runs (`templates/settings.html:76`). Plus
  `static/restart.js:1-19` polling `/settings/restart` during a restart.
- **Conditional requests:** full ETag / Last-Modified / 304 support exists (`internal/web/conditional.go:89-125`)
  but is wired to **API routes only** (`server.go:305-316`); every HTML page is `Cache-Control: no-store`
  (`server.go:522-523`, `:547-548`).
- **Scroll:** sticky table heads exist only inside a fixed-height scroll box at **≥1601 px**
  (`static/css/15-programs.css:9-22`; `18-program.css:206-216` for a program's Scope tab). Below that the whole
  page scrolls and no head sticks.
- **Page sizes:** programs 30 (`programs.go:385`), targets 100 (`targets.go:200`), changes 100
  (`changes.go:330`), disclosed 100 (`disclosed.go:128`), a program's Scope tab 1,000 + "Show all"
  (`programscope.go:68,177-179`).

## 1. P0 — Accepting an invite can block 40 s, and the button lies twice about it

**Experience.** Click *Accept* on a pending invitation. The button reads "Saving…" with a spinner (wrong verb,
right idea). At **8 seconds** it flips back to "Accept", enabled, `aria-busy` removed — while the request is
still running, for up to **40 seconds**. Clicks are still swallowed (`.is-busy{pointer-events:none}`), so the
button looks ready and does nothing. Then the page finally navigates and a flash says it is still going.

**Evidence.**
- `cmd/huntdeck/poller.go:67-76` — `acceptTimeout = 5 * time.Minute`, `acceptWait = 40 * time.Second`;
  `:109-120` waits `acceptWait` inside the **request**.
- `internal/web/acceptinvite.go:15-24,46` — the handler blocks on `s.Poller.AcceptInvite` before redirecting.
- `templates/partials/invite.html:3` — the Accept form (also on the board, `dashboard.html:130`).
- `static/app.js:545-555` — hardcoded `t("Saving…")` and the 8 s restore on line 555; the spinner class from
  `app.js:82-90` stays behind, so the two states contradict each other.
- `static/css/25-accounts.css:45` — `pointer-events: none` while busy.

**Fix.** (a) Per-action label: `<button data-busy="Accepting…">`, read `btn.dataset.busy` at `app.js:549`.
(b) Do not restore before unload — drop the 8 s timer, or keep `aria-busy` and make the wait honest ("Still
working…" after ~10 s). (c) Cheapest structural fix: have `acceptInvite` redirect immediately with
`msg=invite-accepting` and let the invites page carry a `data-live-refresh="10"` row for that program
(`app.js:466-483` already does the rest).

## 2. P1 — The omni search box never shows what you searched, so you cannot refine it

**Experience.** Type `acme payments`, press Enter. You land on `/programs?...&q=acme+payments`; the filter
rail's box is filled in, and the top bar's box — the one you just used — is **empty**. You cannot see the
query, edit it, or tell whether the app searched names or checked a host. On a phone that box is the only
filter you have, so every second search starts by retyping.

**Evidence.** `templates/layout.html:132-136` — the `#omni` input has a `placeholder` but **no `value`**; no
script fills it (`app.js:199-207` only swaps the placeholder, `:238-247` only focuses it). The rail's box does
carry it: `templates/partials/rail.html:9`. Branching: `internal/web/pages.go:50-71` (name → `/programs`,
host → `/match`).

**Fix.** Two lines at the top of `app.js`:

    const q0 = new URLSearchParams(location.search).get("q");
    if (q0) document.getElementById("omni").value = q0;

Then say which branch ran: the form's `aria-label` already promises both, so add a small hint fed from the same
script ("Searching program names" / "Checking this host in scope"), or `data-query="{{.Query}}"` on the
`.omni` form. While there: Escape in the box should clear it.

## 3. P1 — Every GET navigation is silent: filters, sorts, tabs, pagers, saved views

**Experience.** Click a filter chip, a column heading, a page number, a program's tab, or load a saved view.
Nothing changes until the new document paints. Warm local renders are 10-30 ms; the cases that matter are not:
`/targets` at a deep page (53-220 ms the first time, `docs/performance.md:92`), the board after a restart (up to
225 ms, `docs/performance.md:119`), the public read-only copy over the internet (cache misses up to 550 ms,
`ratelimit.go:167-183`), a Scope tab with 1,000 rows. The user sees a dead click and clicks again.

**Evidence.** Busy handling is bound to `submit` only (`app.js:82-90`, `:539-557`). Filter chips are links
(`partials/rail.html:20`), sorts are links (`programs.html:19-31`), the pager is links (`layout.html:154-162`),
rows navigate on click (`app.js:445-461`). A grep of every script for `beforeunload` / `navigate` / `history.`
finds **nothing**.

**Fix.** A 2 px bar under the top bar on click, cleared on `pageshow`, delayed 150 ms so fast pages do not
flicker. ~12 lines and it covers every navigation at once:

    let navTimer = 0;
    document.addEventListener("click", (e) => {
      const a = e.target.closest("a[href]");
      if (!a || e.defaultPrevented || e.button !== 0 || e.metaKey || e.ctrlKey || e.shiftKey ||
          a.target || a.hasAttribute("download") || a.dataset.noNav !== undefined) return;
      const u = new URL(a.href, location.href);
      if (u.origin !== location.origin || u.href.split("#")[0] === location.href.split("#")[0]) return;
      navTimer = setTimeout(() => { document.documentElement.dataset.nav = ""; }, 150);
    });
    addEventListener("pageshow", () => { clearTimeout(navTimer); delete document.documentElement.dataset.nav; });

    /* 03-page.css */
    html[data-nav] .topbar::after { content: ""; position: absolute; inset: auto 0 -1px; height: 2px;
      background: var(--accent); transform-origin: 0 50%; animation: hd-nav .8s ease-out forwards; }
    @keyframes hd-nav { from { transform: scaleX(.08); } to { transform: scaleX(.92); } }
    @media (prefers-reduced-motion: reduce) { html[data-nav] .topbar::after { animation: none; } }

The same handler can set `aria-busy="true"` on `#main` for screen readers.

## 4. P1 — Relative times freeze: "Updated 5m ago" stays "5m ago" all day

**Experience.** Leave a page open. The top bar's "Updated 4m ago" is painted once and never moves. The board's
"Platforms last checked · HackerOne 3h ago" (`dashboard.html:37`) and every row's "25h ago"
(`changes.html:35`, `disclosed.html:44`) are just as frozen. After a night the page asserts something false,
which is worse than saying nothing. The `fresh` highlight (`render.go:171`, 7 days) never expires either, so a
two-day-old program keeps its "new" styling until reload.

**Evidence.** `internal/web/format.go:24-42` (`ago`), `:137-141` (`freshFor`, `recentFor`) — all evaluated at
render; `layout.html:138`; `render.go:180-193` — the `datetime` func formats "2006-01-02 15:04 MST", which
`Date.parse` cannot read reliably. No ticker anywhere: the only timers are `app.js:42,47,89,470-482,500,545-555`,
`restart.js:16,19`, `views.js:96,209`, `channel.js:25`, `vncview.js:29`.

**Fix.** Make the few spots that carry a machine timestamp tick; leave the rest alone.
1. `data-at="{{iso .Updated}}"` on the top-bar span (`layout.html:138`) and on each `.board-status` platform
   (`dashboard.html:37`). `iso` already exists (`render.go:185`) and is the attribute `watch.js:69-76` reads.
2. One 30 s ticker in `app.js` rewriting `textContent` from `data-at` with `Intl.RelativeTimeFormat` (same
   thresholds as `ago`: <1 m "just now", <48 h hours, else days) and `Intl.DateTimeFormat` for the tooltip.
   Only while `!document.hidden` (the pattern at `app.js:470`).
3. Optionally drop `.fresh`/`.recent` from elements whose `data-at` is older than the window, in the same tick.

No server change, ~20 lines, no new strings (the browser formats the times).

## 5. P1 — After a poll, nothing on screen knows it happened (and there is no refresh affordance)

**Experience.** Start a poll from Settings, go back to the board: the tiles ("Open programs", "Changes 24h",
"in scope this week") keep their numbers. Programs' "1,337 open programs", the Changes counts, the header's
"Updated" — all from the render. No refresh button, no stale marker, no "3 new changes". The only place that
tells you (Settings › Poll history) is behind a tab you have no reason to be on.

**Evidence.** Every figure is server-rendered per request — `dashboard.html:30-37`, `programs.html:9`,
`changes.html:9-12`. `data-live-refresh` appears once (`templates/settings.html:76`, gated by `.Live`),
implemented at `app.js:466-483`. Pages are `no-store` (`server.go:522-523`) with no ETag (`conditional.go` is
API-only, `server.go:305-316`).

**Fix (fits the design, cheap).** A "new data" pill fed by the existing cheap endpoint, not by re-fetching the
page:
- `/api/v1/status` already returns `last_polls[].finished_at` and `platforms[].checked_at` (`api.go:36-66`),
  costs 1-10 ms (`docs/performance.md:80`).
- With `data-at` from finding 4 on the top bar, poll every 60 s (only while visible) and, if any
  `finished_at` is newer than the page's `data-at`, show `<button class="pill" data-reload>N new · reload` in
  `.tb-right` (`layout.html:137-141`). A click reloads; nothing moves under the user's hands (the board is
  drag-editable, `board.js:372-408`).
- If you want in-place refresh instead (board only), wire the existing middleware onto `/` the way the API
  routes are wired at `server.go:305-316`. It buffers the body (~30 ms page), sets `ETag`/`Last-Modified`/
  `Cache-Control: no-cache`, and a poller sending `If-None-Match` pays a 304 with no body.

**What I would not do:** SSE (one container, no stream infrastructure, and users put this behind
Tailscale/reverse proxies that buffer; it duplicates the poll-history path that already works), and
`<meta http-equiv="refresh">` (it reloads editable pages under the user — board layout editing, a half-filled
channel form, an open filter rail — and throws away scroll and focus every N seconds).

## 6. P1 — Sticky table heads only exist at ≥1601 px; below that, 100-row lists have no column labels

**Experience.** On a 1440 px laptop (the most common width) `/targets` and `/disclosed` are 100 rows of numbers.
Scroll two screens and the header — with its sort links and its "Bounty / Target score / Added" labels — is
gone. A program's Scope tab is worse: up to 1,000 rows (`programscope.go:68`) with no header at all below
1601 px.

**Evidence.** `static/css/15-programs.css:9-22` — the entire sticky block (`.ptable thead{position:sticky}`,
line 16) sits inside `@media (min-width: 1601px)`; same split at `18-program.css:206`
(`@media (min-width: 1601px) and (min-height: 760px)`). The reason is visible at `04-tables.css:2`:
`.table-wrap{position:relative;overflow-x:auto}` makes the wrapper a scroll container, so a sticky `thead`
inside it can never stick to the viewport.

**Fix.** Below 1601 px, stop the wrapper from being a scroll container and let the head stick under the top bar:

    @media (max-width: 1600px) {
      .plist .ptable > .table-wrap:not(.wide) { overflow-x: clip; }  /* clip: no scroll container, still clips */
      .plist .ptable thead { position: sticky; top: calc(56px + var(--db-h)); z-index: 3;
        background: var(--surface-2); }
      .plist .ptable thead th { border-bottom-color: transparent; box-shadow: inset 0 -1px var(--border); }
    }
    .table-wrap.wide { overflow-x: auto; }  /* only when a Customize choice makes the table too wide */

and in `static/columns.js:121-127`, where `fit()` already knows it needs more room (`if (short > 0)`), toggle
`table.parentElement.classList.toggle("wide", short > 0)`. That keeps the scrollbar for the case that needs it
and gives it up everywhere else. Same two rules for `.scope-table` — and drop the `min-height: 760px` condition
there; a short window needs the sticky head most.

## 7. P1 — The filter rail forgets where you were, and its scrollbar is hidden

**Experience.** On a 900 px-tall screen the rail's ~14 groups are taller than the viewport. You scroll down to
*Status*, click "Paused or closed", the page reloads — and the rail is back at the top. The chip you just set is
off-screen, so undoing it costs another scroll. Every filter change costs a scroll. The rail draws no scrollbar
at all, so nothing hints that nine more groups exist below.

**Evidence.** `static/css/15-programs.css:12` (`.plist > .facets{overflow-y:auto;overscroll-behavior:contain}`),
`:18-19` (`scrollbar-width: none` for `.facets` and `.table-wrap`). Filter links are full page loads
(`partials/rail.html:20`); nothing persists or restores `scrollTop` (`app.js:332-360` only persists whether the
groups are folded).

**Fix.** Eight lines at the end of `app.js`:

    const rail = document.querySelector(".facets");
    if (rail) {
      const key = "huntdeck-rail:" + location.pathname;
      const y = sessionStorage.getItem(key);
      if (y !== null) rail.scrollTop = Number(y);
      else [...rail.querySelectorAll(".fc.on")].pop()?.scrollIntoView({ block: "nearest" });
      rail.addEventListener("scroll", () => { try { sessionStorage.setItem(key, String(rail.scrollTop)); } catch {} },
        { passive: true });
    }

For discoverability, put a `mask-image: linear-gradient(#000 calc(100% - 24px), transparent)` on `.fgroups` —
it only bites when the content overflows.

## 8. P1 — Pagination and filtering throw you to the top of the page, above the rail, and drop keyboard focus

**Experience.** On `/targets` at 1440 px, click *Next* under row 100. The new page starts at the very top:
heading, then the whole filter rail, then the list — you scroll past ~15 groups to reach row 101. Same for
*Previous*, a sort heading, any filter chip. With a keyboard it is worse: focus returns to the document, so the
next Tab starts at the skip link, and a screen reader announces nothing about the new page of results.

**Evidence.** `templates/layout.html:154-162` — the pager builds plain `?page=N` links (`pager.go:57-64`) with no
fragment. The list sections carry no `id` and no `tabindex`: `programs.html:7`, `targets.html:15`,
`changes.html:7`, `disclosed.html:5`. The count/announcement exists only on Programs (`programs.html:9`,
`role="status" aria-live="polite"`); targets `targets.html:17`, changes `changes.html:9` and disclosed
`disclosed.html:7` have a plain span. Nothing restores scroll or focus: no `history.scrollRestoration`, no
`focus()` on load, anywhere.

**Fix (HTML only, no JS).** Give each list `id="list" tabindex="-1"` and have the pager append `#list`:

    // pager.go, url()
    return p.path + "?" + q.Encode() + "#list"

    /* the head must not cover the first row when we land */
    #list { scroll-margin-top: calc(56px + var(--db-h) + 8px); }

Because the section is focusable, loading `#list` also moves the sequential focus start point, so Tab lands on
the first row instead of the sidebar. Then copy Programs' `role="status" aria-live="polite"` onto the other
three counts and include `{{num .Pager.First}}–{{num .Pager.Last}}` so "showing 101–200 of 1,180" is announced.
Filter chips and sort headings should get the same `#list` suffix — `listQuery.with` and `sortURL` are the two
places to add it.

## 9. P2 — The busy label is the same verb for every action, and it deletes the button's icon

**Experience.** *Accept* becomes "Saving…". So do *Test*, *Poll now*, *Run*, *Sign out*, *Restart now*, *Reset to
.env*, *Delete*, and the rail's *Set* (a GET filter!). Where a button had an icon, the icon disappears for good:
`textContent` wipes the children and the restore writes back a string that no longer contains the `<svg>`.

**Evidence.** `static/app.js:545-555` (`btn.dataset.label = btn.textContent` then
`btn.textContent = t("Saving…")`); the string is catalogued at `internal/i18n/catalog/js/zh.json:47` ("保存中…").
Call sites: `partials/invite.html:3`, `notifications.html:28`, `settings.html:30-34,60`, `layout.html:124`,
`partials/rail.html:23`, `ownprogram.html:63`.

**Fix.** `<button data-busy="Accepting…">` per action, with `btn.dataset.busy || t("Saving…")` as the fallback, and
replace only a `<span class="label">` inside the button (the pattern already used at `programs.html:1`). New
strings go in `internal/i18n/catalog/js/zh.json` — `i18ncover_test.go` fails otherwise.

JS — give it `data-busy="Sending a test…"` and `data-no-pending` to opt out of the generic label (finding 9).

## 13. P2 — The notification outbox never updates itself

**Experience.** A message is "waiting" (the outbox retries with backoff). You watch the list; it will say
"waiting" until you reload, even after delivery or after it gave up. Same for the per-channel "N queued" /
"last sent X ago" lines.

**Evidence.** `templates/notifications.html:50-86` (`:79` renders `waiting`/`sent`/`gave up`), `:25`
(`N queued`, `last sent {{ago}}`); no `data-live-refresh` on either panel; the only implementation is
`app.js:466-483`.

**Fix.** Add `data-live-refresh="20"` to the deliveries panel when something is waiting — a three-line
`AnyWaiting bool` on the page data, or `{{if .Waiting}} data-live-refresh="20"{{end}}` in the template. The
mechanism stops itself when the replaced fragment no longer carries the attribute (`app.js:479`).

**Experience.** The Scope tab's search filters rows client-side as you type — the right instinct — but nothing

## Cross-cutting

- **Merge the two submit handlers.** `app.js:82-90` and `:539-557` both bind `submit` with different button
  selectors (`:not([form])` in one, a fallback in the other), different `aria-busy` placement and different
  restore rules. Findings 1 and 9 both come out of that split.
- **Freshness needs one machine-readable attribute.** `iso` exists (`render.go:185`) and `data-at` is already
  used on Changes rows (`changes.html:31`) and read by `watch.js:69-76`. Extending it to ~5 "how fresh is this"
  spots (top bar, board status, poll history, outbox, invites) unlocks findings 4, 5 and 13 with no new
  endpoints.
- **`no-store` is why there is no cheap page refresh.** `conditional.go` already implements the right answer and
  is wired to six API routes. Any page that gets polled needs that middleware, not a second cache design.
- **Order of cheap wins for "no feedback":** navigation bar (3) → per-action labels (9) → copy in-progress (11)
  → inline test result (12). Each is under ~20 lines and none needs a build step.
