# HuntDeck web UI: accessibility and keyboard audit (2026-11)

Scope: `internal/web/templates/**/*.html`, `internal/web/static/app.js`,
`internal/web/static/keys.js`, `internal/web/static/combo.js`,
`internal/web/static/board.js`, `internal/web/static/css/*.css`, checked against
the running instance. Everything below was measured in a browser or read out of
the line quoted; nothing is a guess dressed as a finding.

Instance: `https://huntdeck.dreamxy.top`, build `deploy-202611190549
(1aa6d33db261-dirty)` (the version string in the sidebar), audited 2026-11-19
05:55-06:15 CST, signed in through the access password (never printed, never
written into this report).

Nothing in the repository was modified except this file. No commits.

## How this was verified

- **Browser**: headless Chrome 158.0.8127.37 over CDP (`--headless=new
  --remote-debugging-port`), the session cookie set from a curl login so the
  pages render authenticated. Viewports: 1400x900 and 1280x900 (desktop),
  390x844 (phone), 640x900 and 320x800 (200% and 400% zoom equivalents).
  Emulated `prefers-color-scheme: light|dark` and `prefers-reduced-motion:
  reduce`.
- **Pages**: `/`, `/queue`, `/targets`, `/programs`,
  `/programs/bugcrowd/canva` with every tab (`?tab=scope`, `policy`,
  `stats`, `changes`, `notes`), `/changes`, `/settings` and its
  `accounts`, `polling`, `browser`, `you`, `display` tabs.
- **Names**: the real accessibility tree
  (`Accessibility.getFullAXTree`, ignored nodes dropped, `focusable=false` and
  `disabled=true` dropped) was read on 10 of those pages - not a text-content
  approximation.
- **Keyboard**: real key events (`Input.dispatchKeyEvent` with `text` for
  Enter/Space), a full Tab walk per page reading `document.activeElement`,
  `matches(':focus-visible')` and the computed `outline`/`box-shadow`, then
  Escape/Enter/Space scenarios on each disclosure, dialog and menu.
- **Contrast**: every element with its own text, its colour composited over the
  true background stack (walking ancestors with correct alpha compositing so
  `color-mix()` tints and the translucent top bar are handled), against the
  WCAG 2.1 formula. Large text (>=24px, or >=18.66px bold) at 3:1, everything
  else at 4.5:1.
- **Source**: every finding cites the line that causes it and the line that
  fixes it.

## What passed

Worth recording, because most of the keyboard work here is right and should not
be regressed:

- **Skip link**: first Tab stop on every page, 40px tall, accent background with
  `--on-accent` text, `top: 12px` when focused; Enter moves focus to
  `main#main` (`tabindex="-1"`) and the hash becomes `#main`. Verified.
- **Focus visible**: 70 consecutive Tab stops on `/`, `/queue`, `/targets`,
  `/programs`, `/changes` and 42 on the program page - **0** stops without
  `:focus-visible`, an outline or a focus ring. `01-base.css:40` plus the
  per-control `:focus-visible` rules cover every control that takes focus.
- **No keyboard trap**: traversal wraps (52 stops on `/settings`, 42 on the
  program page) and never cycles inside a widget.
- **Disclosures**: every `<details>`/`<summary>` (theme menu, Export menu,
  Copy targets, Burp / ZAP / Caido, "By asset", the queue's score) opens with
  Enter **and** Space, and Escape closes the `data-menu` ones and puts focus
  back on their `<summary>` (`app.js:397-400`).
- **Dialogs**: `?` opens the shortcuts dialog, focus lands inside it, Escape
  closes it (native `<dialog>.showModal()`).
- **Phone menu**: `Menu` sets `aria-expanded`, Escape closes it and returns
  focus; the menu's links are `display: none` while closed, so they are not
  stray tab stops.
- **Filter rail**: the `Filters` button keeps `aria-expanded` in sync and
  Escape folds it and refocuses it (`app.js:355-380`).
- **Board editor**: `Customize` moves focus to the first drag handle, arrow
  keys move the box, Shift+arrow resizes, `aria-live` announces the mode, and
  Escape leaves with focus back on `Customize`
  (`board.js:182-201,253-279`). A mouse-only feature was given a full keyboard
  path - this is the model the rest of the app follows.
- **Time-zone combobox**: `role="combobox"`, `aria-expanded`,
  `aria-controls`, `aria-activedescendant`, arrows move the active option,
  Enter picks, Escape closes and restores the previous value, Tab closes it and
  leaves (`combo.js:88-107`).
- **Names**: 0 focusable controls without an accessible name across the 10 pages
  read from the AX tree (buttons, links, checkboxes, radios, text fields,
  comboboxes); icon-only buttons carry `aria-label`/`title`.
- **Labels and references**: 0 duplicate ids, 0 `for`/`aria-controls`/
  `aria-labelledby`/`aria-describedby`/`aria-activedescendant` pointing at
  a missing id, on every audited page.
- **Headings and landmarks**: exactly one `<h1>` per page; `main` and named
  `nav` landmarks ("Main", "Back to", "Program sections"); `aria-current` on
  the current nav item and tab.
- **Reduced motion**: with `prefers-reduced-motion: reduce` every transition
  and animation reads `1e-05s` (`01-base.css:44-47`), and "back to the top"
  scrolls with `behavior: auto` (`app.js:684-692`).
- **Reflow**: at 640 CSS px (200% zoom of a 1280 window) no page scrolls
  horizontally and nothing is clipped; the wide tables scroll inside their own
  `.table-wrap`.
- **`lang`**: `<html lang="en">` follows the language switch.

## 1. Platform tags and status chips are below 4.5:1 in the light palette (high)

**Where**: `internal/web/static/css/07-stats.css:40-41` (`.ptag`: text in
`var(--pf)` on a 15% tint of the same colour), `06-chips.css:3-12`
(`.chip` and its `.paused`/`.waiting`/`.private`/`.bbp` variants on
`--*-weak` tints), tokens in `00-theme.css:29-45`.

**Observed** (light palette "Midnight", computed in the page from the composited
background, confirmed against the token values):

| Selector | Text | Background | Ratio | Needs |
|---|---|---|---|---|
| `.ptag.pf-bugcrowd` ("BC") | `#d9580a` | 15% tint over `--surface`: `rgb(249,230,218)` | **3.25** | 4.5 |
| `.ptag.pf-intigriti` ("IGT") | `#0f8f81` | `rgb(219,238,236)` | **3.32** | 4.5 |
| `.ptag.pf-yeswehack` ("YWH") | `#c8183e` | `rgb(247,220,226)` | **4.46** | 4.5 |
| `.ptag.pf-independent` | `#5f6b7a` | 15% tint | **4.45** | 4.5 |
| `.ptag.pf-hackerone` ("H1") on a `--surface-2` row | `#3b5bdb` | `rgb(220,223,249)` | **4.30** | 4.5 |
| `.chip.paused`, `.chip.waiting`, `.chip.partial`, `.chip.running`, `.tag.mod` | `#a15c00` | 15% tint: `rgb(241,231,217)` | **4.23** | 4.5 |
| `.chip.private` | `#c0266d` | 15% tint | **4.43** | 4.5 |
| `.chip.bbp`, `.chip.ok`, `.chip.joined` | `#047857` | 14% tint | **4.15-4.49** | 4.5 |
| `.chip.vdp`, `.chip.creds`, `.chip.tag` | `#1d64c2` | 13% tint | 4.77 | 4.5 (passes) |

These are 10.5px bold text, so they need the full 4.5:1 (the large-text relief
starts at 18.66px bold). Live instances: every row of `/targets`, `/programs`
and `/changes`, the board's "Fresh attack surface" and "Scope diffs" cards, the
Settings poll history, and the queue's program column.

In the dark palette every pair passes (5.45-7.91:1) - the dark tokens are
lighter, so only the light palette is affected.

**Why the palette test missed it**: `TestPaletteContrast` reads the theme
tokens against `--bg`/`--surface`/`--surface-2`; it does not model a token
used as text on a tint of *itself*, which is what `.ptag` and the tinted chips
are.

**Fix** (either, then extend the test):

1. Darken the light-mode tokens that are used as text on a tint - roughly
   `--pf-bugcrowd: #bf4d08`, `--pf-intigriti: #0b7d71`, `--warn: #8a5000`,
   `--good: #036b4d`; or
2. Drop the tints to about 8-10% (`color-mix(... 8%, transparent)`) so the
   background stays nearer `--surface`; the chip still reads as coloured.

Then add to `contrast_test.go` the real pairs - each `--pf-*` on
`color-mix(--pf-* 15%, --surface)`, each `--*-weak` on `--surface` and
`--surface-2` - in both schemes. The existing test would then fail on exactly
the rows above.

## 2. The phone layout deletes Sign out and the language switch (medium)

**Where**: `internal/web/static/css/10-responsive.css:54`
(`.js .nav, .js .sidebar .foot { display: none; }`), with only `.nav` restored
by `.sidebar.nav-open .nav` at line 56. `layout.html:113-128` holds the only
sign-out form and the only language switch (`/logout`, `/settings/language`).

**Observed**: at 390x844, `.sidebar .foot` computes `display: none`; the
sign-out form and the language switch inside it have a 0x0 box. A full keyboard
walk of `/settings` at that width is **41 Tab stops, 0 of them inside
`.foot`, no "Sign out"**. There is no other sign-out control anywhere in the
markup (`grep -rn logout internal/web/templates/` returns the sidebar form and
the sprite symbol only).

**Why it matters**: on a phone - the width where a single-password app is most
likely to be handed to someone else - the account cannot be signed out at all,
and a user who wants the Chinese UI cannot reach the language switch. This is
the only finding here where a control is unreachable rather than awkward, so it
is the most user-blocking one in this report.

**Fix**: show the foot inside the open mobile menu, e.g.

```css
@media (max-width: 700px) {
  .js .sidebar.nav-open .foot { display: flex; position: absolute; top: calc(100% + 6px);
    right: 10px; width: min(280px, calc(100vw - 20px)); padding: 8px 12px; border-radius: 10px;
    background: var(--surface); border: 1px solid var(--border-2); }
}
```

or add a `Sign out` button to `/settings` (which is reachable on a phone) as a
second path.

## 3. Filter chips carry `aria-pressed` on a link, so the state is dropped (medium)

**Where**: `internal/web/templates/dashboard.html:64`
(`<a class="fchip" aria-pressed="{{$f.Has .Key}}">`), the board's kind chips.

**Observed**: with `/?k=wildcard` the active chip is
`<a class="fchip on" aria-pressed="true">Wildcards</a>`; its AX node is
`role=link` with properties `focusable=true, url=...` - **no `pressed`
property**. Chrome (like the other engines) does not support `aria-pressed` on
`role=link`, so it is dropped, not merely mis-announced. Six elements carry it
on the board page. The filter rail in the same codebase uses `aria-current`
(`partials/rail.html:20`), which is the correct pattern for a link that
navigates.

**Why it matters**: a screen-reader user cannot tell which kind filters are on;
sighted users get the filled background and border. WCAG 4.1.2.

**Fix**: use `aria-current="true"` as the rail does, and keep the class for the
visual state; or make the chips `<button aria-pressed>` if they ever stop being
links.

## 4. The queue's score disclosure has no accessible name (medium)

**Where**: `internal/web/templates/queue.html:29`
(`<details class="why-score"><summary>{{printf "%.1f" .Score}}</summary>`)
and the generated arrow at `04-tables.css:71`
(`.why-score > summary::after { content: "▾" }`).

**Observed**: the AX tree names the disclosure **`68.1` plus the arrow** (CSS
generated content is part of the accessible name), role `DisclosureTriangle`,
`expanded: false`. Nothing says "score", nothing says it opens the breakdown;
the column header "Score" is not part of the name, and the cell's `data-label`
is only used by the mobile card layout.

**Fix**:

```html
<summary>{{printf "%.1f" .Score}}<span class="sr-only"> {{T "score, why"}}</span><span class="chev" aria-hidden="true"></span></summary>
```

with the arrow moved from `::after` to the hidden `span` so it stops polluting
the name.

## 5. 320px: the board and Changes scroll sideways (medium, WCAG 1.4.10)

**Where**: `03-page.css:30-33` (`.panel-head` is a non-wrapping flex row and
`.panel-head .aside` is another; its `a.button` has `white-space: nowrap`
via `09-forms.css:14`), and `08-changes.css:46`
(`.activef .sorts { white-space: nowrap }`).

**Observed** at a 320px client width (400% zoom of a 1280 window):

- `/` - `document.documentElement.scrollWidth = 371`. The unclipped overflow
  is `span.aside` (96 to 371: the "Fresh attack surface" head and its "All
  2,076 ->" button at 302 to 371), so the whole page scrolls 51px sideways.
- `/changes` - `scrollWidth = 338`, from `span.sorts` (29 to 338, "Sort by
  Date / ...").
- At 640px (200% zoom) both are clean, and every other page tested is clean at
  320 because its tables scroll inside `.table-wrap`.

**Fix**:

```css
@media (max-width: 480px) {
  .panel-head { flex-wrap: wrap; }
  .panel-head .aside { flex-wrap: wrap; min-width: 0; }
  .activef .sorts { flex-wrap: wrap; white-space: normal; min-width: 0; }
}
```

## 6. Decorative icons are unnamed image nodes (medium)

**Where**: every inline `<svg class="i"><use href="#i-..."/></svg>` in the
templates. The sprite is correctly `aria-hidden="true"` (`layout.html:50`).

**Observed**: role `image` with an empty name and `ignored: false` in the AX
tree: **45** on `/`, **119** on `/targets`, **118** on `/changes`, **52** on
`/programs`, 24 on the program page, 20 on `/settings`, 15 on `/queue`. On
`/targets`, 134 of 140 `svg.i` elements lack `aria-hidden`
(`document.querySelectorAll('svg.i:not([aria-hidden])').length`).

**Why it matters**: in browse mode a screen reader stops on each one ("image", or
nothing), so Targets means about 119 extra stops between the rows that matter.
WCAG 1.1.1 (decorative images must be ignorable).

**Fix**: add `aria-hidden="true"` to the icons. Cheapest route is a template
helper that emits it once (an `icon` func returning
`<svg class="i" aria-hidden="true"><use href="#i-%s"/></svg>`) and then
replacing the inline SVGs.

## 7. Explanations only in a title attribute have no keyboard or touch equivalent (medium)

**Where**: 378 `title="..."` attributes across the templates
(`grep -o 'title="' internal/web/templates/*.html internal/web/templates/partials/*.html | wc -l`). Examples where
the title is the only place the meaning exists: the Targets score's reasons
(`targets.html:46`), the Programs "Requirements" chips (`programs.html:70`),
every sortable column header's definition, and the pay figures' full values
(`pay-title`).

**Observed**: Chrome does not show a native title tooltip when an element takes
keyboard focus, and never on touch. Nothing in the page provides a
focus-triggered equivalent: `aria-describedby` appears once in the whole
template tree (`zonepicker.html:10`, `timezone-now`) and no script reveals a
title on focus. The information is hover-only.

**Fix**: for the handful that carry meaning (score reasons, requirement chips,
money) put the text in an `.sr-only` child or point `aria-describedby` at a
hidden node; decorative titles can stay as they are.

## 8. Text fields are bounded by a 1.45-1.58:1 border (low, WCAG 1.4.11 risk)

**Where**: `09-forms.css:3-5` (`border: 1px solid var(--border-2)`),
`02-shell.css:70-71` (`#omni`), tokens `00-theme.css:24-26`.

**Observed**: `--border-2` on `--surface` is **1.58:1**, on `--bg`
**1.45:1** and on `--side` **1.26:1** in light; dark is the same (1.45 / 1.52).
Fields affected: `#omni` (top search), `.search input` in the filter rail,
`input.interval` on `/settings?tab=polling`, `#tags` on a program page. The
field's own background (`--surface`) is within about 1.1:1 of the page
background, so the border is the only thing marking the control.

**Caveat**: 1.4.11 exempts a control whose text identifies it; a field with a
placeholder and a label is arguably identified by those. Read literally though,
the boundary is under 3:1 and a low-vision user loses the box edge.

**Fix**: give form controls a border that reaches 3:1 against both neighbours
(for example `light-dark(#9b8fc4, #4a5b78)`), or add
`box-shadow: inset 0 0 0 1px color-mix(in srgb, var(--text) 30%, transparent)`
to inputs.

## 9. --faint on the page background is 4.15-4.35:1 (low)

**Where**: `02-shell.css:24` (`.version`, `color: var(--faint)`) and
`02-shell.css:94` (`.tb-title .trail .sep`).

**Observed**: `#6d7788` on `--bg` `#f6f4fd` = **4.15:1**; on `--side`
`#fbfaff` = **4.35:1**; 11px and 13px text. The theme's own comment says
`--faint` is "4.5:1 on the surfaces" - true on `--surface` (4.55) but not on
the two backgrounds these rules use.

**Fix**: use `--muted` for both, or darken `--faint` to about `#626c7e`
(4.6 on `#f6f4fd`), and extend `TestPaletteContrast` to check `--faint` on
`--bg` and `--side` as well as the surfaces.

## 11. Every scrollbar is hidden (low, advisory)

**Where**: `01-base.css:6-7` - `html { scrollbar-width: none }` and
`html::-webkit-scrollbar { display: none }`.

**Observed**: no scrollbar is painted on any page; a "back to the top" button
appears after 700px of scroll (`app.js:681-693`). Keyboard scrolling (PageDown,
Home/End, Space) still works, so nothing is blocked.

**Why it is worth a mention**: a visible scrollbar is the standard "there is
more, and you are here" cue; hiding it hurts low-vision and motor-impaired users
who navigate by scroll position, and it makes a 4,500-row Targets page look
shorter than it is. No WCAG success criterion names it, so it is recorded as
advisory rather than a failure. If the fixed top bar needs the width,
`scrollbar-gutter: stable` gets the same alignment without removing the bar.

## UNVERIFIED

1. **Real screen-reader output.** Names, roles and states come from Chrome's
   accessibility tree. How NVDA, JAWS and VoiceOver phrase them was not heard
   (no Windows or screen reader here). Finding 6's "extra stops" and finding
   7's "hover-only" follow from the tree but were not listened to.
2. **Palettes other than Midnight.** Contrast was measured in the default
   palette (light and dark). Nord and Graphite use the same `color-mix` maths
   with different tokens, so the same failures are likely - Graphite's `--pf-`
   colours are identical to Midnight's - but they were not measured.
   `TestPaletteContrast` covers the tokens, not the tints.
3. **/login.** The CDP profile already held a session cookie, so `/login`
   redirected to `/` and the page was not audited. Its template shows
   `label for` and an `aria-describedby` Caps Lock note, but that is reading,
   not measurement. A fresh `Target.createBrowserContext` would settle it.

## Reproducing

The harness is three small pieces (kept out of the repo):

```js
// 1. Tab walk: real Tab events, then read the focused element
await send("Input.dispatchKeyEvent", { type: "rawKeyDown", key: "Tab", code: "Tab", windowsVirtualKeyCode: 9 });
await send("Input.dispatchKeyEvent", { type: "keyUp", key: "Tab", code: "Tab", windowsVirtualKeyCode: 9 });
await evalJS("(() => { const el = document.activeElement; const cs = getComputedStyle(el); return { el: el.tagName, fv: el.matches(':focus-visible'), outline: cs.outlineWidth }; })()");

// 2. Enter and Space need text, or a button does not activate at all
await send("Input.dispatchKeyEvent", { type: "keyDown", key: "Enter", code: "Enter", text: "\r", windowsVirtualKeyCode: 13 });

// 3. Names: the real tree, not textContent
const { nodes } = await send("Accessibility.getFullAXTree", { depth: -1 });
nodes.filter((n) => !n.ignored && n.role?.value === "link" && !n.name?.value);
```

For contrast, walk the ancestors compositing `background-color` with correct
alpha (the `color-mix()` tints are translucent), then apply the WCAG
relative-luminance formula. An `over()` that forces alpha to 1 after the first
layer reports every tinted chip as 1:1 - that is the trap, and the numbers above
come from the corrected version.

### The `title=` finding: decision

378 elements carry information in `title`, which neither focus nor touch
reveals. The fix is not a global one: a tooltip component would be a new UI
surface (positioning, dismissal, touch targets) and would replace a browser
behavior the page relies on today.

What will happen instead, when it is worth doing: the titles that explain a
*number* (the score breakdown, the facets' counts) move into the visible text,
which the pages mostly do already; the rest stay as hover hints, and the one
case where the title is the only source (a chip's requirement) is a candidate
for the "before you test" box, which is where requirements already live.

Recorded as accepted, not as fixed.
