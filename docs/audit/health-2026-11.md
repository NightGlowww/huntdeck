its own context and no stake in the code being right: one against the queue,
the scoring and the policy/AI paths, one against the web layer. This file is
the merged result. The per-finding detail lives in
[queue-review-2026-11.md](queue-review-2026-11.md) and
[web-ui-review-2026-11.md](web-ui-review-2026-11.md).

## Known-gaps, stated rather than hidden

- **HuntQueue's acceptance line is unmeasured, and now on a clock.** The design
  asks for top-10 capture 10% above HuntScore's on 6 of 8 point-in-time cuts.
  `hunt_scores` held two days; it holds **three** since 2026-11-19 00:05Z, written
  by the server's 30-minute ticker with no one running a command (verified in
  four places: `status`, `doctor`, `backtest`, the queue page's footer). At one
  row a day the eighth cut lands around **2026-11-24**, and `huntdeck backtest`
  then has enough history to answer. Until then the harness prints the cut count
  and the shares it can compute, which are 0% because the windows are empty.
- **The readiness factor barely bites on today's data.** `Flips` reaches 12
  programs (0.8), `NoAutomation` none of the candidates, and `NeedsCreds` has
  **no stored source** — the column is wired and commented. On this data the
  factor still evaluates near 1.0.
- **The login browser runs without its sandbox**, because Chrome aborts here
  with it on (measured: exit 134). The blast radius is written down in
  docs/configuration.md; the profile is 0700 and the container is non-root with
  all capabilities dropped.
- **The gated half of the queue is unexercised.** No target is gated today
  (every candidate has scope), so the Blocked panel and its counts are covered
  by unit tests only.
- **Dead CSS was not removed.** A scan found 113 selectors no template mentions,
  but most are built in JS or by templates indirectly (`bx-*`, `facet`,
  `charted`); removing them without a browser pass would risk breaking the board
  editor, so the list stays a lead, not a change.


## Addendum: the UI audit is closed (2026-11-19)

All fifteen findings in [ui-ux-2026-11.md](ui-ux-2026-11.md) are now fixed. Two
of them needed a channel or a large program to be visible, and were verified
with a seeded webhook channel in `TestNotificationsWithAChannel` rather than
against the running instance.

Three things came out of closing it that are worth keeping:

1. **A page-level check must print the status and the title first.** A
   "nothing renders" conclusion was drawn twice from requests to
   `/notifications`, which is a 404: the page lives at `/settings/notifications`.
   The short path now redirects, and the rule is: status, then title, then
   the claim.
2. **A panel that only renders when it has rows hides its own controls.** The
   notifications page hid "Recent messages", its channel filter and its status
   filter behind `{{if .Deliveries}}`; a fresh channel therefore had no way to
   be filtered or even seen. It renders with channels now, with an empty state.
3. **"Show all" is still a page.** The Scope tab capped its first view at
   1,000 rows but let `?all=1` render every entry; a program with thousands
   now stops at 2,000 and says the export carries the rest.

The queue's numbered findings in
[queue-review-2026-11.md](queue-review-2026-11.md) keep their own resolution
table; nothing there is outstanding except the accepted one.

### How the page tests are shaped

`TestListPagesRenderWithData` fetches every page in the navigation — and every
program-detail tab — with the seeded platform data, and each case names a
marker taken from that seed (`Acme Corp`, `acme.example`). Two things it is
for: a template branch that only runs with rows once shipped a 500 on
`/queue`, which no empty-state test could see; and a marker that does not come
from the seed turns a healthy page into a false alarm (the first draft looked
for `example.com` when the seed uses `acme.example`).

The same rule applies to the queue: `TestQueuePageRendersBuiltRows` builds a
queue and then asserts the expanding score and its loss line are present.

## Backups, verified rather than assumed (2026-11-19)

| What | How many | Where |
|---|---|---|
| Pre-migration snapshots | 4 | `/data/backups/huntdeck-<ts>-schema-vNNNN.db` |
| Daily archives | 2 | `/data/backups/huntdeck-backup-YYYYMMDD.tar.gz` |

The archives come from the host's scheduler, not from the app: HuntDeck only
snapshots the database before a schema upgrade. A restore was dry-run against
the newest archive:

```
$ huntdeck restore --from /data/backups/huntdeck-backup-20261119.tar.gz \
      --data /tmp/restore-check --dry-run
would restore into /tmp/restore-check: database v61, with the platform
sessions; nothing written
```

A backup is only a backup if it opens: that command unpacks it, checks the
schema and the row counts against the archive's own manifest, and writes
nothing. It is worth running after changing the schedule, and after an upgrade
that adds a migration — the archive is then a version behind (v61 here against
v62), which is expected: the restore migrates it forward on the next start.

## How to re-run a review

Both reviews were run by subagents with their own context, given a shared task
with a write scope of one file. The brief that worked: scope the files, name the
class of finding wanted (correctness and user-visible behaviour, not style),
require file:line plus a concrete fix, require live verification where possible
and an UNVERIFIED tag where not, and forbid edits outside the report.
